# docs/

チューニングの記録を、種類ごとのディレクトリに連番で積み上げます。
既存の文書は書き換えず、新しい番号の文書を足します。差分がそのまま履歴になり、後から時系列で読めるようにするためです。

## ディレクトリ

- `overview/` は全体像の資料を置く。人間が指示した時点のスナップショットとして作る。
- `design/` はチューニング施策の design doc を置く。施策を入れる前に書く。
- `results/` はチューニング結果を置く。施策を deploy してベンチした後に書く。
- `retro/` は振り返りを置く。人間が指示した時点で作る。

## ファイル名

- `NNN_<英小文字のスラッグ>.md` の形にする。例：`001_add-indexes.md`。
- `NNN` はディレクトリごとの 3 桁の連番にする。そのディレクトリの最大の番号に 1 を足す。
- `design/` と `results/` は、同じ施策に同じ番号とスラッグを付ける。`design/003_x.md` の結果が `results/003_x.md` になる。
- 設計を書かずに入れた小さな施策の結果も、`design/` 側の番号を空けて同じ規則で付ける。

## 各文書に書くこと

すべての文書の冒頭に、書いた日時と基準のコミット（短い SHA）を書く。

### overview/

- 業務ドメイン、システム構成、コードの構成、エンドポイント、データモデル、主な処理の流れを書く。
- その時点で入っている施策と、スコアの推移を書く。
- 前のスナップショットからの変化を、冒頭に短くまとめる。

### design/

- 目的：何を速くするか。
- 根拠：計測の数字（alp・pt-query-digest・pprof）と、コードの該当箇所。
- 変更内容：どのファイルをどう変えるか。
- レギュレーションへの影響：再起動・`/initialize`・データの永続性。
- 確かめ方：何がどう変われば成功か。

### results/

- 対応する design（無ければ「なし」）と、deploy したコミット。
- スコアの前後と pass / fail。`notes/scores.tsv` の行を引く。
- 計測の変化：ボトルネックがどこからどこに移ったか。
- 分かったこと、効かなかったこと、次の候補。

### retro/

- やったことと効果を、スコアと一緒に時系列で並べる。
- 的確だったアプローチと、うまくいかなかったアプローチを書く。
- 次に活かすことを書く。

## 書き方

- 日本語の「です・ます」調で、一文を短く区切る。
- 推測は推測と書き、計測した値とは分けて書く。
- 太字などの装飾は使わない。図は Mermaid で描く。
- ファイル名・識別子・コマンドは、コードの表記のまま書く。
