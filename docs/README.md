# docs/

docs/ には 3 種類の文書を置きます。種類ごとに、書く人・書くタイミング・書き換えてよいかが決まっています。いつ書くかの手順は、CLAUDE.md の「出来事ごとの手順」が正です。

## 種類

- 生きた文書：kit/（道具ごとの手引き）と flow/（場面ごとの手順）。リポジトリ直下の README.md と CLAUDE.md も同じ扱いにする。
  - 道具や手順を変えたら、その変更と同じコミットで書き換える。
  - 書くのは変更したセッション自身で、main に直接コミットする。
- 積み上げる文書：overview/・design/・results/・retro/。
  - 書き換えず、新しい番号の文書を足す。差分がそのまま履歴になり、後から時系列で読めるようにするため。
  - 書くのはサブエージェント doc-writer で、docs ブランチにコミットする。呼び出した Claude が、直後に `make docs-merge` で main に取り込む。
- 記録：scores.tsv。
  - `make bench`・`make score`・`make portal` が追記し、その場でコミットする。手で書き換えない。

## 生きた文書

### kit/

- 道具（make のターゲットのまとまり）1 つにつき 1 枚にする。ファイル名は道具の名前にする（例：bench.md）。
- 節は「役割・いつ使うか・動かし方・確かめ方・更新のしかた」の 5 つに固定する。
- 「動かし方」は、スクリプト冒頭のコメントと make help を指すだけにして、引数の説明を写さない。
- ほかの文書はリンクにせず、パスで書く。リンクで辿る入口は README.md の目次だけにする。
- 道具を足したら、README.md の目次にリンクを足す。make lint が漏れとリンク切れを見つける。

### flow/

- 道具をまたぐ手順だけを置く（first-time・resume・contest）。
- 施策 1 回の流れは CLAUDE.md の「出来事ごとの手順」が正とし、flow/ には写さない。

## 積み上げる文書

### ディレクトリ

- `overview/` は全体像の資料を置く。人間が指示した時点のスナップショットとして作る。
- `design/` は施策の design doc を置く。施策（アプリ・server/・sql/ を変えるコミット）のコードを書く前に、必ず書く。
- `results/` は施策の結果を置く。施策を deploy してベンチした後に、必ず書く。取りやめた施策も「取りやめ」として書く。
- `retro/` は振り返りを置く。人間が指示した時点で作る。

### ファイル名

- `NNN_<英小文字のスラッグ>.md` の形にする。例：`002_template-cache.md`。
- design の `NNN` は、design/ と results/ を通して最大の番号に 1 を足す。results は、対応する design と同じ番号とスラッグにする。`design/003_x.md` の結果が `results/003_x.md` になる。
- overview/ と retro/ の `NNN` は、ディレクトリごとの最大の番号に 1 を足す。

### 各文書に書くこと

すべての文書の冒頭に、書いた日時と基準のコミット（短い SHA）を書く。

#### overview/

- 業務ドメイン、システム構成、コードの構成、エンドポイント、データモデル、主な処理の流れを書く。
- その時点で入っている施策と、スコアの推移を書く。
- 前のスナップショットからの変化を、冒頭に短くまとめる。

#### design/

- 目的：何を速くするか。
- 根拠：計測の数字（alp・pt-query-digest・pprof・vmstat など）と、コードの該当箇所。
- 変更内容：どのファイルをどう変えるか。
- レギュレーションへの影響：再起動・`/initialize`・データの永続性。
- 確かめ方：何がどう変われば成功か。make bench の `E=` に書く「期待した動き」もここに書く。

#### results/

次の見出しを、この順で使う。hooks（scripts/hooks/session-start.sh）が「## 次の候補」を読むので、見出しの文字は変えない。

- `## 対応する design`：design のパス（無ければ「なし」）と、deploy したコミット。
- `## スコア`：スコアの前後と pass / fail。docs/scores.tsv の行を引く。
- `## 計測の変化`：ボトルネックがどこからどこに移ったか（make analyze の結果）。
- `## 分かったこと`：分かったこと、効かなかったこと。
- `## 次の候補`：まだ手を付けていない候補を、すべて書く。直前の results の候補のうち、手を付けていないものは書き写す（次の施策は、最新の results だけを読んで選ぶため）。

#### retro/

- やったことと効果を、スコアと一緒に時系列で並べる。
- 的確だったアプローチと、うまくいかなかったアプローチを書く。
- 次に活かすことを書く。

## 記録（scores.tsv）

- 列は time（手元の時刻の YYYYmmdd-HHMMSS）・rev（deploy 済みのコミット）・pass・score・memo・expect（make bench の `E=`）。
- results からは、該当する行をそのまま引く。

## 書き方

- 日本語の「です・ます」調で、一文を短く区切る。
- 推測は推測と書き、計測した値とは分けて書く。
- 太字などの装飾は使わない。図は Mermaid で描く。
- ファイル名・識別子・コマンドは、コードの表記のまま書く。
